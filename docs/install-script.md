# The `curl | bash` installer

`curl -fsSL https://validationcloud.io/install.sh | bash` installs `valcloud` for people who have no Node.js, or an old one. People who manage Node.js themselves keep `npm install -g @validationcloud/cli`. How it is built and shipped is in [CONTRIBUTING.md](../CONTRIBUTING.md#releasing); this page records why it looks the way it does. The design survived an adversarial debate (attacker, defender, independent judge, then a verification pass); the killed ideas are listed at the end so they are not proposed again.

## Design

- **Two downloads, nothing else.** The installer fetches a pinned Node.js tarball from nodejs.org and `valcloud.mjs` from the GitHub release. It never runs npm, so the user's `.npmrc`, `~/.npm` permissions and registry mirrors cannot affect it.
- **One bundle per release.** `valcloud.mjs` is an esbuild bundle of `dist/cli.js` with all dependencies inlined, so the installer needs no `node_modules` and the runtime needs no resolution at all. The integration suite runs against it on the pinned Node.js (`pnpm run test:bundle`).
- **License notices travel with the bundle.** `build-release.ts` appends the LICENSE and NOTICE text of every package in the esbuild metafile. The MCP client ships pre-bundled chunks that inline further packages (ajv, fast-uri and others); the sourcemap beside a chunk names them and `scripts/vendored-licenses.json` holds their texts. A package without an entry fails the build, and so does any map-less bundled file that is not on the reviewed list in `scripts/bundled-packages.json` (the two map-less client chunks were read: rolldown runtime helpers and a re-export barrel, no third-party code), so a client upgrade that inlines something new cannot ship without its notice.
- **The script is a release asset.** `/install.sh` redirects to `releases/latest/download/install.sh`, so a commit merged to `main` reaches customers only after CI passes and a release publishes. The script in the repo is a template (`scripts/install.sh.in`) with `@…@` placeholders, rendered per release by `scripts/render-installer.ts`.
- **Pins live in the script.** `scripts/node-runtime.json` holds the Node.js version and one SHA-256 per platform tarball, taken from a `SHASUMS256.txt.asc` that `pnpm run bump-node` verifies with gpg against the eight active releasers' fingerprints committed in `scripts/node-release-keys.json` (a good signature by any other key, or a revoked or expired one, fails). The render step inlines the pins as literals, and the bundle's own SHA-256 is written in at the same time. The installer does not fetch `SHASUMS256.txt` at install time.
- **Platforms.** macOS 13.5 or newer (arm64, x64; Rosetta shells get arm64), Linux x64 and arm64 with glibc 2.28 or newer, Linux x64 with musl and `libstdc++`. The macOS and glibc floors equal what the pinned binaries need and are checked before any download. The C library is decided by `getconf GNU_LIBC_VERSION` first, so a glibc host that also has the `musl` package is still glibc.
- **Nothing is replaced until it works.** Downloads go to `$INSTALL_DIR/.install.XXXXXX`; the runtime and the bundle are checked (`--version`) and moved into place with `mv`; the new launcher is a `mktemp` file in the bin dir that runs before it replaces the old one. The PATH line is written next, and cleanup comes last and is best effort: a failed delete is a warning, never a failed install. Cleanup removes only the installer's own names (`runtime/node-v*-*`, `lib/valcloud-[0-9]*.mjs`, and `.install.*` directories and `.valcloud.tmp.*` files older than an hour), and it first re-reads the launcher and keeps the runtime and bundle it names, so a run that finished meanwhile keeps its files. A killed run leaves either the old install or the new one.
- **It refuses to touch what is not its own, or to run where it would do harm.** An existing launcher without the marker line, or a symlink, stops the run before any download, and so does a bin dir it cannot write to. A non-empty install directory without `.valcloud-installer` is refused, so `VALCLOUD_INSTALL_DIR=$HOME` cannot delete anything. `.` and `..` components in either directory, a backslash in the install dir (Node.js cannot run a module from such a path) and `"`, `$`, a backtick or a backslash in the bin dir (it is written into a startup file) are refused. Root through `sudo`, and a `HOME` owned by someone else, are refused, because they leave root-owned files in a user's home; root in a container (no `SUDO_USER`) is fine. Every failing step names itself and the fix.
- **PATH.** One marked line is appended to the shell's startup file (zsh, with `ZDOTDIR` as zsh itself reports it; bash; fish `conf.d`; other shells get the line printed). On Linux, bash gets `.bashrc` when it exists, otherwise the first login file that exists, as on macOS. A file the installer creates holds only that line. If the file cannot be written, the installer says so and prints the line. The user's PATH is otherwise untouched, so `open` and `xdg-open` still work for `valcloud auth login`.
- **No login prompt.** `auth login` listens on a loopback port for five minutes and hangs over SSH. The installer ends with `Next: valcloud auth login`.

## Trust and limits

- The trust root is GitHub (the script, the bundle hash, the Node.js hashes) plus TLS to nodejs.org. Whoever can publish a release, or change the redirect on validationcloud.io, can run code on customers' machines. Turn on GitHub immutable releases once the draft-then-publish flow of `@semantic-release/github` is confirmed to work with them, and restrict who can edit the redirect.
- The Node.js runtime is patched only when the user re-runs the installer after a release that bumps it, which is why Node.js bumps release (`fix(runtime):`).
- **Proxies and certificates.** The launcher runs `node --use-env-proxy --use-system-ca <bundle>`, so `fetch` honours `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` and trusts the OS certificate store (TLS-inspecting proxies). Evidence: both flags tested on Node.js 24.22.0 against squid, tinyproxy and mitmproxy; both are needed for a TLS-inspecting proxy, and without a proxy the first changes nothing and the second only adds the system store to the trusted certificates. `NODE_EXTRA_CA_CERTS` covers CAs that are not in the OS store, and a local `VC_MCP_URL` needs `NO_PROXY=localhost,127.0.0.1`. An earlier claim that these flags hang `fetch` came from a test proxy without a `connect` handler. Re-run the proxy matrix on every Node.js pin bump. Known risk, not fixed here: on undici 7 (Node.js 24) a proxy that closes `CONNECT` without replying makes `fetch` hang forever (nodejs/undici#3897, fixed in undici 8.6.0); the fix is a request timeout and an explicit exit in the CLI itself.
- Linux arm64 on musl, glibc older than 2.28, 32-bit systems, FreeBSD and Windows (outside WSL) are unsupported.
- About 118 MB installed; about 175 MB peak on a first install and about 290 MB during a runtime bump.
- Concurrent runs are unsupported (`flock(1)` does not exist on macOS). Every step is an atomic rename, and cleanup keeps what the launcher names, so a run that has already replaced the launcher keeps its files. A run still in progress is not protected: another run's cleanup can delete the bundle or runtime it has moved into place but not yet linked, and two runs can replace the same runtime under each other. The usual result is a failed launcher check with a message; in a narrow window the launcher can end up pointing at a deleted file. Re-run the installer after the other run finishes.
- The launcher hardcodes absolute paths. Moving `~/.valcloud` requires a re-run.
- Not yet verified on real hardware: Intel macOS and Rosetta (the darwin-x64 hash is verified, the branch is small), and the Webflow redirect to an external URL.

## Rejection ledger

One line per idea that was killed, and why.

| Killed idea                                                                        | Cause of death                                                                                                                                                                                                     |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Install through the private runtime's `npm install`                                | `bin/npm` is `#!/usr/bin/env node`, which fails with rc 127 when no node is on PATH, and it exposes the install to the user's npmrc, `~/.npm` EACCES and registry mirrors.                                         |
| Launcher pointing into an npm package layout                                       | `location=global` in npmrc moves the package, and published 0.1.0 has no `bin/valcloud`.                                                                                                                           |
| Verifying against a same-origin `SHASUMS256.txt` at install time                   | It adds nothing over TLS; replaced by per-platform hashes pinned in the script.                                                                                                                                    |
| "Log in now? [Y/n]" prompt via `/dev/tty`                                          | `-r /dev/tty` is true without a tty, so `read` fails under `set -e` after a good install, and `auth login` hangs for five minutes over SSH.                                                                        |
| Redirecting `/install.sh` to `main` on raw.githubusercontent                       | Any merged, unreleased commit would run on customer machines.                                                                                                                                                      |
| "Skip the download if the runtime dir exists"                                      | An interrupted extraction persists forever; replaced by a temp dir, `mv` and a `node --version` check.                                                                                                             |
| Extracting the full Node.js tarball                                                | 199 MB for one binary; only `bin/node` and `LICENSE` are extracted (118 MB).                                                                                                                                       |
| Always creating `~/.bash_profile` on macOS                                         | It shadows an existing `~/.profile`.                                                                                                                                                                               |
| `fish_add_path`                                                                    | It needs fish 3.2; `conf.d` with `set -gx` works everywhere.                                                                                                                                                       |
| A profile line hardcoding `$HOME/.local/bin`                                       | It ignored `VALCLOUD_BIN_DIR`.                                                                                                                                                                                     |
| Pointing old-glibc users to `npm install -g`                                       | Node.js 22 needs glibc 2.28 too, so the hint was a dead end.                                                                                                                                                       |
| Detecting musl by `/lib/ld-musl-*` first                                           | It refuses glibc hosts that have the `musl` package installed (`musl-tools`); glibc is decided first now.                                                                                                          |
| `--legal-comments=eof` as license compliance                                       | It keeps one notice and drops the MIT and Apache-2.0 notices of the bundled dependencies; the notices are generated from the metafile now.                                                                         |
| The claim "latest never lacks assets"                                              | `@semantic-release/github` ignores a missing asset and publishes anyway; the build fails on a missing asset and a smoke job installs from `releases/latest`.                                                       |
| Untyped or `chore` Node.js and dependency bumps                                    | The default rules release nothing for them, so no customer would get the fix; they are `fix(runtime):` and `fix(deps):`.                                                                                           |
| A `releaseRules` entry naming only `scope: "runtime"`                              | It also matches `feat(runtime):` and demotes it to a patch; each rule names its type too.                                                                                                                          |
| Validating the launcher after `mv -f`                                              | A failed check leaves a broken launcher in place; it is validated before the move.                                                                                                                                 |
| Cleanup by `runtime/*` and `valcloud-*.mjs` globs                                  | It deletes foreign files under a custom install dir; cleanup matches only the installer's own names and requires the marker file.                                                                                  |
| Deleting every `.install.*` directory on each run                                  | It removes another run's work directory; only leftovers older than an hour go.                                                                                                                                     |
| `NODE_EXTRA_CA_CERTS` alone, with no proxy flags                                   | It does not make `fetch` use a proxy at all, and the "flags hang `fetch`" reason for leaving them out was a test proxy without CONNECT support; the flags are in the launcher now.                                 |
| A lock around the install                                                          | `flock(1)` is absent on macOS; atomic renames and post-write validation bound the damage.                                                                                                                          |
| Objection: "`$SHELL` unset crashes under `set -u`"                                 | Bash fills `SHELL` from passwd, and the code reads `${SHELL:-}`.                                                                                                                                                   |
| Objection: "deleting a runtime under a running process breaks it"                  | Unix unlink semantics; a node process finished normally after its runtime directory was removed.                                                                                                                   |
| Custom `releaseRules` for `fix(runtime)` and `fix(deps)`                           | Custom rules replace the default breaking-change rule, so `fix(runtime)` with a `BREAKING CHANGE:` footer released a patch; the defaults already release every `fix` as a patch.                                   |
| Starting a script only when `process.argv[1] === import.meta.filename`             | It fails open through a symlink: the script exits 0 and builds nothing; `import.meta.main` is used.                                                                                                                |
| Trusting every key in nodejs/release-keys, cloned unpinned                         | Retired and revoked keys signed as valid; the active fingerprints are committed and revoked, expired and unverifiable signatures fail.                                                                             |
| One try at `releases/latest` in the smoke job, run only on an implicit `success()` | GitHub can lag, a skipped job looked green, and nobody saw it; the job installs from the pinned URL, then polls `latest` with backoff, and fails visibly.                                                          |
| Aborting the install when the final cleanup fails                                  | A working update exited 1 and skipped the PATH setup; cleanup is best effort and runs last.                                                                                                                        |
| Skipping sourcemap entries that are not pnpm store paths                           | A new inlined package would lose its notice silently; unparseable entries and a bundled file with no sourcemap fails the build unless `scripts/bundled-packages.json` lists it (or its whole package) as reviewed. |
